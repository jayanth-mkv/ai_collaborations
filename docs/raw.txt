how to host a lslm model like haru ai
To host a Listening-while-Speaking Language Model (LSLM) like Haru-4B, you run the official inference server from the higurashi-ai/Haru GitHub repository using PyTorch (for NVIDIA GPUs), MLX (for Apple Silicon), or vLLM-Omni for production scaling. [1]
Because full-duplex speech models process incoming audio and generate outgoing speech simultaneously in 133 ms frames, they cannot be hosted with standard text-only engines like Ollama and require a real-time audio streaming runtime. [1, 2]
Hardware & Setup Prerequisites
GPU / Memory. You need an NVIDIA GPU with at least 12 GB of VRAM (or an Apple Silicon Mac with unified memory) to load the 10.5 GB model weights. [1, 2]
Audio Hardware. Use wired headphones and a wired microphone to avoid echo feedback loops and prevent the 100+ ms latency added by Bluetooth devices. [1]
Voice Reference Clip. Prepare a clean, single-speaker .wav audio file (between 3 seconds and 3 minutes long) for the model to clone as its speaking voice, as Haru ships without default voices. [1]
Option 1: Host Locally with PyTorch & Web UI (NVIDIA GPU)
The official repository includes a built-in server and browser interface for local real-time conversations. [1]
Clone the repository and install dependencies.
bash
git clone https://github.com/higurashi-ai/Haru && cd Haru
pip install -e ./haru
Use code with caution.

Start the local inference server. This command automatically downloads the open weights from the Haru-4B Hugging Face page.
bash
python -m haru.server --hf-repo higurashi-ai/Haru-4B
Use code with caution.

Launch the voice interface. Open http://localhost:8998 in your browser, upload your reference voice clip, configure a character card, and start speaking. [1]
Option 2: Other Deployment Environments
Depending on your hardware or scaling goals, you can use two alternative runtimes included in the project: [1]
Apple Silicon (macOS). Use the native MLX implementation and macOS app included in the GitHub repository to run the model directly on M-series chips. [1]
Cloud & Multi-User Production. Deploy on a cloud GPU (such as an NVIDIA RTX 4090, A100, or L4) using the official vLLM-Omni plugin to handle concurrent real-time voice streams. [1]
Option 3: Custom Python Integration
If you are embedding the LSLM into your own voice application or telephony pipeline, you can stream 24 kHz audio frames directly using the DuplexSession API: [1]
Developers can programmatically load the model and manage real-time audio streaming sessions using the DuplexSession and HaruModel classes provided in the package. [1]
Note: Haru-4B is a pretrained base model for natural conversational speech rather than an instruction-tuned assistant, which means custom pipelines or specific tool-calling requirements may necessitate additional fine-tuning. For complete code examples and API usage details, consult the documentation on Hugging Face. [1, 2]

Full-duplex speech models must process incoming audio and generate outgoing speech simultaneously in 133 ms frames, which requires the parallel processing power of a dedicated GPU to keep up in real time.
Why a CPU-Only Server Fails for Full-Duplex Audio
Real-Time Latency Requirement. A full-duplex model must complete a forward pass and vocoder audio synthesis faster than every 133 ms audio chunk. On a standard CPU without hardware acceleration, generating a single frame takes several seconds, causing severe audio stuttering and broken conversations.
Heavy Model Architecture. Haru-4B is a 4-billion-parameter model (~10.5 GB weights) paired with continuous audio encoders and neural vocoders. Running this pipeline on CPU memory bandwidth bottlenecks audio streaming immediately.
Lack of Native CPU Optimization. The official Haru-4B runtimes rely on CUDA (PyTorch / vLLM-Omni) for NVIDIA GPUs or Metal (MLX) for Apple Silicon, rather than quantized CPU inference engines like llama.cpp.

Use a Cascaded CPU Voice Pipeline. If you are strictly locked into a CPU-only Linode server, you cannot run an end-to-end LSLM, so you would need to build a traditional turn-based pipeline using lightweight CPU models (e.g., whisper.cpp for speech-to-text, a small quantized LLM via llama.cpp, and Piper for text-to-speech).

No, you cannot convert Haru-4B into a standard llama.cpp (GGUF) model with existing tools, though a skilled C++ developer could theoretically rewrite parts of it. While the model's core "brain" is a standard text model that llama.cpp understands, its custom audio components and real-time voice loop are completely unsupported by llama.cpp.
1. The Basics: How llama.cpp Works
To understand why conversion fails, it helps to look at how standard models are converted into GGUF (the file format used by llama.cpp):
Standard Text Models. Normal LLMs take text tokens in and spit text tokens out, one word at a time.
The Conversion Process. You run a Python script (convert_hf_to_gguf.py) that maps the model's math layers to pre-written C++ code inside llama.cpp. If llama.cpp does not already have C++ code written for a specific model's architecture, the conversion script simply crashes. [1, 2]
2. Why Haru-4B Cannot Be Converted Directly
According to the Haru-4B Hugging Face documentation, the model is built from three distinct pieces: [1]
The Text Backbone (Supported): Haru uses Qwen3.5-4B as its core language model. llama.cpp already supports Qwen architectures. [1]
The VibeVoice Audio Codec (Unsupported): Haru uses a causal acoustic tokenizer that chops raw 24 kHz audio into 64-dimensional continuous latents every 133 milliseconds. llama.cpp has no built-in support for this audio encoder or decoder. [1]
The MeanFlow Audio Head (Unsupported): Instead of predicting text tokens, Haru uses a custom 4-layer neural network (MLP head) with MeanFlow sampling to generate continuous audio waves directly from the model's hidden state. llama.cpp is designed to sample discrete text tokens, not continuous audio vectors. [1]
Because llama.cpp expects text in → text out, it does not know how to sum user audio, model audio, and text into a single position every 133 ms. [1]
3. What It Would Take to Make It Work (Theoretical Path)
If an engineer wanted to port Haru-4B to run on CPU via C++ (ggml, the math library behind llama.cpp), they would have to build a custom C++ runtime from scratch rather than running a simple converter:
Split the Model. Convert only the Qwen3.5-4B backbone into GGUF format. [1, 2]
Write Custom C++ Kernels. Manually write C++ implementations for the VibeVoice audio codec and the MeanFlow sampling head using ggml tensor operations. [1, 2]
Rebuild the Streaming Loop. Write a custom audio-streaming server in C++ to replace llama-server, handling microphone input and speaker output every 133 ms. [1, 2]
The Hardware Catch. Even after months of C++ engineering, a standard CPU without vector acceleration (like AVX-512) would still likely struggle to finish the math within the strict 133 ms real-time window. [1]
4. Practical Workaround for Your Linode CPU Server
If your goal is to run a voice AI on a CPU-only Linode server using llama.cpp, skip end-to-end LSLMs and connect three lightweight C++ tools together:
Ears (Speech-to-Text): Run whisper.cpp to transcribe user speech into text on the CPU.
Brain (LLM): Run a quantized Qwen3.5-4B or Llama-3 GGUF model via llama.cpp (Q4_K_M quantization runs smoothly on modern server CPUs).
Mouth (Text-to-Speech): Run Piper TTS to convert the LLM's text reply back into audio in under 100 ms on a CPU. [1, 2, 3, 4]

Yes, it is technically possible to rewrite Haru-4B from scratch in C++/ggml, and it can run efficiently—but only on modern, high-core-count CPUs with fast memory.
However, it is a significant systems-engineering project rather than a quick script, and running it on a cheap Linode CPU tier will still hit physical hardware bottlenecks.
1. The Math: Will It Run Efficiently on a CPU?
To keep up with real-time conversation, your custom C++ engine must execute one full cycle in under 133 milliseconds (7.5 frames per second). Here is what happens in every single 133 ms frame:
Memory Bandwidth Bottleneck. Quantizing the 4B Qwen backbone to 4-bit (Q4_K_M) shrinks the model weights from ~10.5 GB down to ~2.5 GB. To run 7.5 forward passes per second, your CPU must read 2.5 GB × 7.5 = ~18.75 GB/s of data from RAM just for the transformer weights.
Linode Hardware Reality.
A Shared CPU Linode (e.g., $5–$40/month) shares memory channels with other tenants and lacks modern vector extensions, resulting in ~5–10 GB/s effective bandwidth. Your model will lag behind real time.
A Dedicated CPU Linode (e.g., 16+ dedicated AMD EPYC cores with AVX-512) offers 40–80+ GB/s memory bandwidth, allowing a 4-bit quantized model to finish a frame in ~40–70 ms—fast enough for real-time full-duplex audio.
2. What You Actually Have to Build (The Blueprint)
Because llama.cpp is strictly a text-token generator, you wouldn't use llama.cpp directly. Instead, you would use ggml (the underlying C tensor library that powers llama.cpp and whisper.cpp) to build a custom C++ binary.
Here is the exact engineering roadmap:
Extract & Quantize the Backbone (Qwen3.5-4B):
Use llama.cpp as a library (libllama) or extract the Qwen transformer graph in ggml.
Use llama_decode with inputs_embeds (raw floating-point embeddings instead of discrete text token IDs), which llama.cpp already supports for multimodal models.
Port the VibeVoice Audio Codec to ggml:
Inspect the Python/PyTorch architecture of the VibeVoice encoder and decoder in the Haru repository.
Rewrite its 1D convolutions, causal padding, and residual blocks using ggml_conv_1d and custom C++ ring buffers to process 24 kHz audio chunks (3,200 samples per 133 ms frame).
Note: Keep the audio codec in FP16 (half-precision)—quantizing audio vocoders to 4-bit usually destroys voice quality and adds metallic static.
Port the MeanFlow Audio Head:
Write a small 4-layer MLP and the ODE/flow-matching sampling loop in C++ using ggml_mul_mat to convert the transformer's hidden state into the 64-dimensional latent vector.
Build the Real-Time Audio Loop:
Implement a multi-threaded C++ WebSocket or WebRTC server using a lock-free ring buffer.
Thread 1: Captures incoming 24 kHz audio frames from the user.
Thread 2: Runs the ggml inference pass (Encoder → Sum Embeddings → Qwen Backbone → MeanFlow Head → Decoder) strictly under 133 ms.
Thread 3: Streams generated PCM audio back to the client.
3. Key Trade-Offs to Expect
Engineering Effort: Expect 2 to 6 weeks of dedicated C++ and ggml development, mostly spent debugging tensor shapes, causal convolution padding, and audio drift.
Cost Efficiency: A Dedicated CPU Linode with 16–32 cores and enough memory bandwidth to hit <133 ms latency typically costs $140–$280+/month. By comparison, renting an on-demand cloud GPU (like an RTX 4000 Ada or L4) often costs the same or less while running the native PyTorch code with zero C++ rewrite.
Best Use Case for Rewriting: Building this in C++/ggml makes the most sense if you want to deploy Haru-4B locally on edge devices, laptops, or mobile phones without Python or CUDA dependencies.

Yes, you can build this and submit pull requests to three primary open-source repositories so the entire community can run Haru-4B on CPUs and edge devices. Both Haru-4B (Apache 2.0) and llama.cpp (MIT) use permissive open-source licenses that actively welcome community contributions. [1, 2]
1. Where to Submit Pull Requests (By Scope)
Depending on how you structure your code, split your contributions across these specific repositories:
higurashi-ai/Haru on GitHub (Primary Target for Full App)
What to PR: A new haru_cpp/ or haru_ggml/ runtime directory alongside the existing haru/ (PyTorch) and haru_mlx/ (Apple Silicon) folders.
Why it fits: The official repository is already structured around multiple hardware backends. Adding a dependency-free C++/ggml runtime and CLI/WebSocket server here gives Haru users an immediate CPU and cross-platform option. [1]
ggml-org/llama.cpp on GitHub (For Audio Codec & Multimodal Support)
What to PR: Support for the VibeVoice audio codec inside tools/mtmd (llama.cpp's multimodal module) and gguf-py conversion scripts.
Why it fits: llama.cpp accepts PRs that add new vision or audio encoders to its multimodal library (libmtmd) so that inputs_embeds workflows work out of the box. Note that llama.cpp generally avoids merging custom full-duplex streaming servers or specialized continuous ODE sampling heads into its core CLI, making higurashi-ai/Haru the better home for the full duplex loop. [1]
Hugging Face Hub (For Pre-Converted Weights)
What to publish: Once your conversion script works, upload the ready-to-use GGUF files (such as Haru-4B-Q4_K_M.gguf and vibevoice-codec-f16.gguf) to a public Hugging Face repository so users do not have to run the Python conversion step themselves.
2. Recommended Open-Source Workflow
Before writing thousands of lines of C++, follow standard open-source etiquette to ensure your PR gets merged smoothly:
Open an Architecture Discussion First. Post an Issue on the higurashi-ai/Haru repository outlining your proposed directory layout, CMake build setup, and GGUF weight-splitting format. Maintainers often share helpful internal tensor details when they see a serious contributor.
Keep Dependencies Zero or Minimal. Both ggml and higurashi-ai/Haru benefit most if your C++ port compiles cleanly with standard CMake and uses lightweight, header-only libraries (like dr_wav for audio I/O and ixwebsocket or cpp-httplib for the streaming server). [1, 2]
Include a Python Verification Script. When submitting a ggml port, include a small test script that compares the C++ output tensors of the VibeVoice encoder and MeanFlow head against the original PyTorch tensors from Haru-4B to prove numerical accuracy.
